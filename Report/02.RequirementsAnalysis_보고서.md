# Gilded Rose Requirements Analysis Report

## 1. Purpose

This report summarizes the C++ implementation-oriented requirements analysis for the Gilded Rose C++17 legacy project.

The analysis was created from `GildedRoseRequirements.txt`, `README.md`, and the current C++ project structure. Its main goal is to clarify business rules, boundary conditions, string-based item classification risks, and Google Test scenarios before implementing or refactoring `updateQuality()`.

## 2. Created Analysis Document

- File: `docs/requirements_analysis.md`
- Location: `docs` directory
- Target project: Gilded Rose C++17
- Test framework: Google Test
- Build system: CMake
- Main purpose: define QA-oriented behavior expectations for future implementation and test work

## 3. Scope of Analysis

The document reorganizes the original requirements into C++ implementation concerns:

- Item-specific business rules for Normal, Aged Brie, Backstage Pass, Sulfuras, and Conjured items
- `std::string` comparison and branching cautions
- Boundary conditions for `quality` and `sellIn`
- Sulfuras exception handling
- New Conjured item behavior
- Google Test scenario candidates

This scope is intended to support both characterization testing and behavior-preserving refactoring.

## 4. Business Rule Summary

| Item Type | sellIn Behavior | quality Behavior | Special Rule |
| --- | --- | --- | --- |
| Normal | Decreases by 1 daily | Decreases by 1 before sell date, by 2 after sell date | Never below 0 |
| Aged Brie | Decreases by 1 daily | Increases by 1 before sell date, by 2 after sell date | Never above 50 |
| Backstage Pass | Decreases by 1 daily | Increases by 1, 2, or 3 as concert approaches | Becomes 0 after concert |
| Sulfuras | Does not change | Does not change | `quality` stays 80 |
| Conjured | Decreases by 1 daily | Decreases twice as fast as Normal | Decreases by 2 or 4 |

The key implementation point is that Sulfuras must be excluded from all normal `sellIn` and `quality` mutation paths.

## 5. C++ Implementation Risks

The current implementation classifies item behavior by comparing `Item::name` strings. This creates several QA risks:

- Exact string comparison using `==` is sensitive to spelling, spaces, punctuation, and case.
- `std::string::find()` must be compared with `std::string::npos`.
- `if (name.find("Conjured"))` is incorrect because a match at index `0` evaluates as false.
- Conjured should have a clearly defined matching rule, preferably a `"Conjured"` prefix check.
- The branch order should prevent Sulfuras from entering any general update path.

These risks should be covered by focused tests before changing the legacy logic.

## 6. Boundary Conditions

The analysis identifies the following high-risk boundary values:

- `quality == 0`: decreasing items must not become negative.
- `quality == 49`: increasing items must not exceed 50.
- `quality == 50`: Aged Brie and Backstage Pass must remain capped.
- `quality == 80`: Sulfuras exception must remain unchanged.
- `sellIn == 1`: last day before expiration.
- `sellIn == 0`: update transitions item into expired state.
- `sellIn == -1`: already expired item.

For the existing Gilded Rose update flow, `sellIn == 0` is especially important because the item becomes expired during the update and the post-expiration rule is applied in the same call.

## 7. Conjured Requirement

The new Conjured requirement is defined as follows:

- Conjured items degrade in `quality` twice as fast as normal items.
- Before expiration, Conjured `quality` decreases by 2.
- On or after expiration, Conjured `quality` decreases by 4.
- Conjured `quality` must never go below 0.
- Conjured items still decrease `sellIn` by 1 each day.
- A representative test name is `"Conjured Mana Cake"`.

This requirement should be implemented as a distinct item category rather than as an accidental Normal item variant.

## 8. Google Test Planning Result

The analysis document defines 24 Google Test scenario candidates covering:

- Normal item degradation
- Minimum quality boundary
- Expired item behavior
- Aged Brie increase and maximum quality boundary
- Backstage Pass threshold behavior at 10 and 5 days
- Backstage Pass drop to 0 after concert
- Sulfuras immutability
- Conjured double degradation
- Conjured lower-bound quality protection
- Conjured string classification

These scenarios can be used as the acceptance baseline before refactoring `GildedRose::updateQuality()`.

## 9. Result

The project now has a dedicated requirements analysis document at `docs/requirements_analysis.md`.

The document is suitable for senior C++ QA review, Google Test case design, and future implementation of the Conjured requirement while preserving the legacy Gilded Rose behavior.

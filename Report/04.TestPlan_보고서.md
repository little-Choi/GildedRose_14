# Gilded Rose Test Plan Report

## 1. Purpose

본 보고서는 Gilded Rose C++17 프로젝트의 테스트 계획 산출물을 요약한다.

테스트 계획은 기존 레거시 동작을 보존하면서 신규 `Conjured` 요구사항을 안전하게 검증하기 위해 작성되었다. 특히 Google Test의 `TEST_F` 기반 단위 테스트, 핵심 경계값, 예외 케이스, gcov/lcov 기반 커버리지 측정 전략을 명확히 정의하는 것을 목표로 한다.

## 2. Created Test Plan Document

- File: `docs/test_plan.md`
- Location: `docs` directory
- Target project: Gilded Rose C++17
- Test framework: Google Test
- Build system: CMake
- Coverage tools: gcov/lcov
- Main purpose: define QA-led unit test scope, priority, boundary cases, exceptional cases, and coverage strategy

## 3. Scope of Test Planning

테스트 계획서는 다음 항목을 포함한다.

- `GildedRose::updateQuality()` 대상 단위 테스트 범위
- `TEST_F` 기반 테스트 픽스처 권장 구조
- Normal, Aged Brie, Backstage Pass, Sulfuras, Conjured 아이템별 테스트 우선순위
- `quality`와 `sellIn`의 고위험 경계값 케이스
- Sulfuras, Backstage Pass, Conjured 관련 예외 및 특이 케이스
- gcov/lcov 기반 커버리지 목표와 측정 절차
- 커버리지 미달 시 테스트 보강 전략

## 4. TEST_F Unit Test Strategy

기존 `TEST(GildedRoseTest, ...)` 방식은 단일 케이스 확장에는 단순하지만, 아이템 타입별 공통 준비와 검증 패턴을 반복하게 된다.

따라서 테스트 계획서는 `TEST_F` 기반 픽스처 도입을 권장한다. 공통 픽스처는 다음 책임을 가진다.

- 테스트용 `std::vector<Item>` 준비
- 단일 아이템 업데이트 헬퍼 제공
- 업데이트 후 첫 번째 아이템 상태 접근
- 테스트명만으로 아이템 타입, 입력 상태, 기대 동작을 파악할 수 있는 명명 규칙 제공

권장 테스트명 패턴:

- `Normal_SellInPositive_DecreasesQualityByOne`
- `AgedBrie_Quality49AfterSellDate_DoesNotExceed50`
- `BackstagePass_SellInZero_DropsQualityToZero`
- `Sulfuras_Expired_DoesNotChange`
- `Conjured_SellInZero_DecreasesQualityByFour`

## 5. Test Priority Summary

| Priority | Focus Area | Description |
| --- | --- | --- |
| P0 | 핵심 요구사항 회귀 방지 | Normal, Aged Brie, Backstage Pass, Sulfuras, Conjured의 대표 동작 검증 |
| P0 | 품질 경계 불변식 | `quality`가 0 미만 또는 50 초과가 되지 않도록 검증 |
| P0 | Sulfuras 예외 | `sellIn`과 `quality`가 모두 변경되지 않음을 검증 |
| P0 | Conjured 신규 요구사항 | 일반 아이템보다 2배 빠르게 품질이 감소함을 검증 |
| P1 | 경계값과 오프바이원 | Backstage Pass의 `sellIn 11/10`, `6/5`, `1/0` 전환점 검증 |
| P1 | 문자열 판별 | 정확한 특수 아이템 이름과 Conjured 접두사 판별 검증 |
| P2 | 유지보수성 보강 | 빈 목록, 다중 아이템, 반복 업데이트 등 보조 시나리오 검증 |

## 6. Boundary Case Summary

테스트 계획서는 다음 경계값을 고위험 입력으로 정의한다.

| Boundary | Meaning | Main Test Target |
| --- | --- | --- |
| `quality == 0` | 품질 하한 | Normal, Conjured 감소 후 0 미만 방지 |
| `quality == 1` | 하한 근접 | 만료 후 2 또는 4 감소 시 0으로 보정 |
| `quality == 49` | 상한 근접 | Aged Brie, Backstage Pass 증가 후 50 초과 방지 |
| `quality == 50` | 일반 상한 | 증가형 아이템이 50을 유지하는지 검증 |
| `sellIn == 0` | 판매 기한 당일 | 업데이트 후 만료 규칙 적용 여부 검증 |
| `sellIn == -1` | 이미 만료 | 만료 후 규칙이 계속 적용되는지 검증 |

특히 `sellIn == 0`은 현재 구현 흐름에서 업데이트 중 `sellIn`이 `-1`로 감소한 뒤 만료 후 규칙이 같은 호출 안에서 적용되므로 우선순위가 높다.

## 7. Exceptional Case Summary

### Sulfuras

- `"Sulfuras, Hand of Ragnaros"`는 `sellIn`과 `quality`가 모두 변경되지 않아야 한다.
- `quality`는 일반 상한 50의 예외로 80을 유지한다.
- `sellIn 0`, `sellIn -1`에서도 불변이어야 한다.

### Backstage Pass

- `sellIn > 10`: quality 1 증가
- `6 <= sellIn <= 10`: quality 2 증가
- `1 <= sellIn <= 5`: quality 3 증가
- `sellIn == 0` 또는 `sellIn < 0`: quality 0
- 증가 구간에서도 quality는 50을 초과하지 않아야 한다.

### Conjured

- `"Conjured Mana Cake"`처럼 `"Conjured"`로 시작하는 이름을 대표 테스트 데이터로 사용한다.
- 판매 기한 전에는 quality 2 감소, 판매 기한 당일 및 이후에는 quality 4 감소를 검증한다.
- quality 감소량이 현재 quality보다 커도 0 미만이 되면 안 된다.
- 기존 특수 아이템 규칙과 충돌하지 않도록 분기 우선순위를 검증한다.

## 8. Coverage Target

테스트 계획서는 다음 커버리지 목표를 제안한다.

- Line coverage: 90% 이상
- Branch coverage: 85% 이상
- `GildedRose::updateQuality()` function coverage: 100%
- 신규 `Conjured` 분기 추가 시 해당 분기 line/branch coverage: 100%

현재 `updateQuality()`는 중첩 조건문과 문자열 기반 분기가 많기 때문에 단순 라인 커버리지보다 브랜치 커버리지를 중요 지표로 본다.

## 9. gcov/lcov Measurement Strategy

커버리지 측정은 GCC 또는 Clang 계열 도구chain에서 별도 coverage 빌드 디렉터리를 사용하는 방식을 권장한다.

대표 절차:

```bash
cmake -S cpp -B build-coverage -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_FLAGS="--coverage -O0 -g" \
  -DCMAKE_EXE_LINKER_FLAGS="--coverage"
cmake --build build-coverage
ctest --test-dir build-coverage --output-on-failure
lcov --capture --directory build-coverage --output-file coverage.info
lcov --remove coverage.info '/usr/*' '*/_deps/*' '*/test/*' --output-file coverage.filtered.info
genhtml coverage.filtered.info --output-directory coverage-report
lcov --summary coverage.filtered.info
```

Windows 환경에서는 MinGW/MSYS2 또는 WSL 기반 GCC 사용을 권장한다. MSVC 환경에서는 gcov/lcov 대신 OpenCppCoverage 또는 Visual Studio Coverage 사용을 별도 검토해야 한다.
